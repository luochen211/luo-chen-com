08 / 17 · DEPENDENCIES
CONTRACT FIRST
THE REAL UPSTREAM

不是等待后端，
而是先冻结 Contract

以登录功能为例：前端、后端和测试共同依赖的，并不是某一方“全部完成”，而是接口输入、输出和错误码已经明确。

依赖写成“API 完成”会制造串行；写成“Contract 明确”才能一次解锁三条支线。

10 / 17 · READY QUEUE
FOUR STATES
STATUS IS A DECISION

每个 Issue 只能处在一个明确状态

— 01 / READY

现在开工

依赖已满足，让 Agent 或开发者领取。

— 02 / BLOCKED

明确等待

必须写清正在等谁，不提前改核心文件。

— 03 / REVIEW

先过关

已有 PR，优先处理 CI、Review 和合并。

— 04 / DONE

重新计算

合并并关闭后，立即解锁下一批 Ready。

13 / 17 · CONTEXT BOUNDARY
ONE TERMINAL · ONE EPIC
MIXED CONTEXT

一个窗口
跨多个 Epic

上下文、分支、检查和复盘来回切换，AI 的工作记忆会被污染。

  • 范围漂移
  • 误改其他模块
  • 依赖关系混在一起
BOUND CONTEXT

一个窗口
只管一个 Epic

另一个父 Issue 就新开终端，重新加载需求、子 Issue 和局部 DAG。

  • 记忆边界清晰
  • 分支与 PR 可追踪
  • 复盘能回到同一任务图

16 / 17 · PROMPT KIT
COPY · ADAPT · RUN
REFERENCE · COPY AFTER TALK

六条指令，直接交给 Agent

01 / INVENTORY

先盘点，不写代码

列出 Issue / PR，标出依赖、重复和首批 Ready。

02 / VISUALIZE

画主图与局部图

分别生成 Epic 主 DAG 与当前 Epic 子图。

03 / QUEUE

只输出四种状态

Ready / Blocked / Review / Done。

04 / EXECUTE

只执行 #XX

复述目标、范围、验收，只修改相关文件。

05 / RECALCULATE

合并后重读状态

读取 PR、CI、Issue，输出新 Ready Queue。

06 / POSTMORTEM

冲突先回到图

定位错误依赖边，必要时暂停下游。
