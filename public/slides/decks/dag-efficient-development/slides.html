09 / 16 · READY QUEUE
FOUR STATES
STATUS IS A DECISION

每个 Issue 只能处在一个明确状态

— 01 / READY

现在开工

依赖已满足，让 Agent 或开发者领取。

— 02 / BLOCKED

明确等待

必须写清正在等谁，不提前改核心文件。

— 03 / REVIEW

先过关

已有 PR，优先处理 CI、Review 和合并。

— 04 / DONE

重新计算

合并并关闭后，立即解锁下一批 Ready。

10 / 16 · FAILURE CASE
PR #154
CONFLICT POSTMORTEM

真正浪费时间的
不是写代码

PR #154 的代价来自执行前没有明确：#41 依赖哪些上游、谁该先合并、谁必须等待。

01

上游尚未稳定

多个下游分支同时修改同一批基础文件。

02

冲突被当成局部技术问题

二进制冲突、分支落后、重开 PR 反复补丁式处理。

03

CI 与合并顺序缠在一起

状态重跑、PR 被提前关闭，真正原因是依赖顺序错误。

15 / 16 · PROMPT KIT
COPY · ADAPT · RUN
SIX COMMANDS

把复杂方法压成六类指令

01 / INVENTORY

先盘点，不写代码

读取 Open Issues / PR，输出分类、疑似依赖、重复与第一批 Ready。

02 / VISUALIZE

生成主 DAG 与局部 DAG

展示 Epic 依赖、完成度，以及未完成 Epic 的子任务图。

03 / QUEUE

输出四种状态

Ready / Blocked / Review / Done；Blocked 必须说明在等谁。

04 / EXECUTE

只执行 #XX

复述目标、范围、验收；只改相关文件，运行检查后开 PR。

05 / RECALCULATE

合并后重新读取状态

确认 PR、CI、Issue，然后列出新解锁的 Ready Queue。

06 / POSTMORTEM

冲突先回到 DAG

判断是局部代码冲突，还是依赖顺序错误；必要时暂停下游。
